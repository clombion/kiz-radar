# merge-review-v1: decide whether two artist records are the same artist

The events database lists dance artists (teachers, DJs, performers) extracted from festival descriptions.
A script grouped identical spellings; it could not decide the pairs in your batch. For each pair, decide
whether side A and side B are the same artist.

Files (paths relative to /Users/datum/para/0_mac_inbox/kizomba-world):
- Input:  `data/merge_review/input/<BATCH>.json` = {"batch", "pairs": [{"pair_id", "key_a", "key_b",
  "reason", "a": [mentions], "b": [mentions]}]}; each mention gives the event, date, city, event country,
  role, the name as written, style, stated country and the original line.
- Output: `data/merge_review/output/<BATCH>.json`
- Schema: `schemas/merge_review.json` (read it first)

## Deciding

- `merge` — the evidence shows one artist: e.g. the same stage name with a DJ prefix on one side
  ("DJ J-Kee" / "J-Kee") and the same country; a spelling variant or typo of a distinctive name
  ("Poema Beatz" / "Dj Poema beat"); a first name and the full name with the same partner or the same
  country and style ("Nico Berrettoni" / "Nicola Berrettoni").
- `separate` — the evidence shows two artists: different countries, different full names that only share
  a first name ("Sara" / "Sara Martins" with nothing else in common), or genuinely different names one
  letter apart (Daniel / Daniela, Maria / Marina).
- `unsure` — the evidence does not settle it. Prefer `unsure` over a guess: a wrong merge joins two
  people's event histories.

Common first names (Sara, Laura, Daniel, Maria, Alex…) are weak evidence on their own; distinctive stage
names are strong evidence.

## Output

One JSON object: `{"batch": "<BATCH>", "prompt_version": "merge-review-v1", "decisions": [...]}` with
exactly one decision per input pair: `{"pair_id", "key_a", "key_b", "decision", "rationale"}` — copy
`pair_id`, `key_a` and `key_b` from the input; `rationale` is one sentence naming the evidence used.
